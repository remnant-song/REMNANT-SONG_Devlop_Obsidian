## 根因

`atob()` 解码 base64 得到的是**二进制字符串**（每个字符码点即字节值 0-255）。中文 `实` 的 UTF-8 编码是 3 字节 `E5 AE 9E`，`atob()` 后变成 3 个"字符" `å` `®` `ž`（码点 0xE5/0xAE/0x9E 在 Latin-1 中对应的字符），这就是乱码的来源。

**修复原理**：`atob` → `Uint8Array`（字节数组）→ `TextDecoder('utf-8')`（正确解码多字节 UTF-8）→ 正确的中文文本。

两个加载器的数据获取路径完全不同，差别就在这：

## GitHub 路径 — 两条腿走路

```
文件树：api.github.com REST API        → JSON（含文件列表）
文件内容：raw.githubusercontent.com    → 纯文本，带 CORS 头
```

`raw.githubusercontent.com` 是 GitHub 专门为跨域读取设计的 CDN 域名，响应头自带 `Access-Control-Allow-Origin: *`，内容直接就是源文件文本，fetch 拿到即用。

## Gitee 路径 — 只有一条腿

```
文件树：gitee.com/api/v5 REST API      → JSON（含文件列表）
文件内容：gitee.com/.../raw/...        → 纯文本，但 ❌ 无 CORS 头，浏览器拦截
          ↓ 被迫改用
          gitee.com/api/v5/contents/   → JSON（含 base64 编码内容），✅ 有 CORS
```

Gitee 的 raw 域名没有配置 CORS 响应头，浏览器直接拒绝跨域读取。只能退回用 API 的 contents 端点，但 API 返回的是 JSON 包裹的 base64 内容，多了一层解码。

## 一图胜千言

| | GitHub | Gitee |
|---|---|---|
| 文件树 | API 直接拿 | API 直接拿 |
| 文件内容 | raw CDN 直接给纯文本 | raw 不给 CORS → 被迫走 API → base64 解码 |
| 额外步骤 | 无 | ① CORS 绕路 ② base64→UTF-8 解码 |

**一句话：GitHub 的 raw 域名是"对前端友好的 CDN"，Gitee 的 raw 域名是"只给浏览器地址栏看"的。**
